## What

A run record now names a project-store policy locator only when the store actually holds that policy, the reader says where a run's policy bytes are now and which CLI command follows, and the dashboard explains a `failed` record whose telemetry reads `done` (ADR-326). `write_run_record(policy_name=…)` names `assets/<name>` only when that file exists with the recorded digest at record time, and records the trainer's own copy as `artifacts.policy` (`train/<name>`). `read_run_record` adds `policy_store` — `stored` (verified by digest through a stamp-keyed cache and lock of its own, bounded at 4 MiB), `digest mismatch`, `unstored`, `refused`, `none` — with the retained trainer copy and `next_action`: `cadex asset --project <project-dir> --put <project-dir>/runs/<run>/train/<name>`, or a new walk when nothing is retained; pre-ADR-326 records that name no run-local copy resolve it at the trainer's one fixed place only when it exists. The identity card gains a **policy store** row, and the note on a failed run with `done` telemetry says training itself finished (iteration N of M, policy saved by the trainer) and the failure came after it, in the observation or recording, not in the trainer. Regression: `test_browser_explains_a_failed_observation_whose_training_finished` (headless Chromium, fixture with `lark109-engine`'s exact shape, including the store write seen on the next poll with the record unchanged), four reader/writer tests, and the record fixture's policy digest corrected to the bytes it stores. Live receipt on the persistent operator URL: `docs/probes/lark-fresh/policy_store110.py`, `policy-store110-evidence.json`, pinned by `test_lark_fresh_evidence.py`; cited in LIFECYCLE.md (D8 row) and README.md. Docs: `docs/CLI.md` record, reader and dashboard sections; ADR-326.

## Why

Criteria D8 (failed runs remain understandable, with the next CLI action) and D10 (the persistent dashboard shows explicit failed/pending states and never misleads on the current run) — the critic's named unit and the previous iteration's own handoff bet. The critic banned the plan's clearance bet and asked for one criterion and the smallest thing that moves it; this is that unit, done as asked: the record writer fixed at the source rather than the bounded drivers patched (a record that names only what exists makes every driver honest at once, and the reader's disk-read store state makes a later `asset --put` visible with no record rewrite), plus the dashboard explanation and the real `lark109-engine` receipt on port 8765.

## Method

Read the writer, reader, server telemetry and `review.js` identity/artifact rendering, the three probe drivers' record calls, and the `lark109-engine` record on `ot5-lark-copy85` (status `failed`, telemetry `done` at 99/100, `policy.asset` named, `assets/` without it, `train/lark109-engine.cxpolicy` present with the recorded sha256). Implemented writer, reader, page and tests; record and targeted browser tests green. Restarted the `cadex-operator-review` unit (no trainer active, checked with the probe's `trainers()`), confirmed over the private address that the API read `lark109-engine` as `unstored` with `artifacts.policy` resolved and `lark96-restart`/`lark109-engine2` likewise. Wrote the live probe: fresh visit (selects `lark109-engine2`), select `lark109-engine`, capture note/store/artifact rows and screenshot, download the trainer's copy through the page (64,384 bytes, sha256 equal to the record), run the command the page named, wait for the open page to flip.

**First live attempt failed on my own advice.** The page said `cadex asset --put runs/<run>/train/<name>` "from the project directory"; run there, the CLI's `--project` default of `./.cadex` created a nested project *inside* the Lark copy and stored the asset in it (`ot5-lark-copy85/.cadex/{PROGRESS,ARCHITECTURE,DECISIONS}.md, assets/`), so the page never flipped. Inspected and deleted that directory (created minutes earlier, mine alone; nothing else under the copy changed), corrected the advice to name `--project <project-dir>` and the `--put` path against it, updated tests, docs and ADR to say why the directory is named twice, restarted the unit, and repeated the probe with the command run from `/`.

Second attempt passed: CLI exit 0 in 0.839 s, store row sha256 equal to the record; the open page flipped to `stored` 0.202 s later with one navigation entry, status still `failed`, note unchanged, `problems` emptied, `project_artifacts.policy` now `retained · download`; fresh visit still selects `lark109-engine2` and shows `stored` for `lark109-engine`; `run.json` bytes unchanged; all 601 `runs/` files unchanged; `assets/` gained exactly `lark109-engine.cxpolicy` with prior assets unchanged; accepted revision `6f826037044a…`/digest `c039961cd41d…` unchanged; service MainPID identical before and after; no trainer seen.

Full CLI suite on the intermediate code found a real interaction: policy digests went through the video verification lock, so `test_two_browser_clients_share_cold_video_verification` stalled the second client's poll behind a cold video hash before it reached the video. Gave policy digests their own `lru_cache` and lock. Final verification: `pixi run python -m pytest cli/tests -q` — **478 passed, 1 skipped in 477.85 s, exit 0**; `git diff --check` clean. Unit restarted once more on the committed code (no trainer): MainPID 559912, active, `Restart=on-failure`; `/api/project` serves `ot5-lark-copy85`, 15 runs, fresh visit `lark109-engine2`, `lark109-engine` `stored`, `lark96-restart` and `lark109-engine2` `unstored`. No engine, payload, shell or dependency change, so no build, engine suite or packaged gate was run.

## Result

True now: a record's `policy.asset` is a fact about the disk at record time; every run on the persistent Lark copy shows an honest store state and a runnable next action; a failed run whose training finished is explained on the page; `lark109-engine`'s policy is in the store with its recorded digest and its record untouched. Port 8765 serves the working copy under its unit on the committed code.

Concerns and assumptions for the next iteration: (1) `lark96-restart` and `lark109-engine2` are `ok` runs whose policies were never stored (their bounded drivers never `asset --put`); the page now says so and names the command, and the reader does not treat an `ok` run with an unstored policy as a problem — a judgement left open. (2) `asset --put` moves the manifest's `latest_candidate`/`updated_at` as any engine open does; the accepted identity does not move. (3) The CLI's `--project` default is `./.cadex`; any advice or document that says "run from the project directory" without `--project` is wrong in the same way mine was. (4) Same-machine browser only; no second-device claim. No new dependency.

Handoff bet (a different criterion from the banned one): **D5/D8 — an `ok` run with an unstored policy is a retention gap**: either have the two bounded drivers store their policy through the same `cadex asset --put` `train.py` uses and prove it on the next real bounded run on the persistent copy, or make the reader list `ok` + `unstored` under `problems` with the command, with a browser regression; then decide whether to store `lark96-restart`/`lark109-engine2` through the page's advice. Alternative if that looks blocked: the long-term rung — repeat the lifecycle from a clean project to expose dependencies on the Lark fixture.

Dispatch closed: 1 unit — record writer names a stored policy only when the store holds it, reader and dashboard explain the failed-observation run's state and next CLI action, live receipt on the persistent URL, ADR-326.
