# Fresh biped lifecycle report (D9)

Verified against source: 2026-09-12. [Cadex-new]

This is the report the charter's D9 asks for: the fresh biped's whole
recorded lifecycle — create, save, reopen, train, record, review, revise,
retrain, revisit — with the D1–D8 evidence each step rests on, the retained
artifact identities a reader needs to interpret every run, and the
comparison of both designs over the same declared seeds. It is assembled
from what the project retains, by a script that only reads:

```bash
COPY="$HOME/cadex-projects/ot5-biped-copy29"; URL="http://$(tailscale ip -4):8765/"
PYTHONPATH=cli:cli/tests pixi run python docs/probes/operator-review/verify.py \
  "$URL" "$COPY" shin55-final > /tmp/operator-check.json
PYTHONPATH=cli pixi run python docs/probes/reed-lifecycle/report.py "$COPY" \
  --operator-check /tmp/operator-check.json > docs/probes/reed-lifecycle/report.json
pixi run python -m pytest cli/tests/test_lifecycle_report.py
```

[report.json](report.json) is that output against the real project on
2026-09-12: the accepted identity, twelve run identities with the model view
the dashboard serves for each, the common-seed comparison recomputed from the
committed evaluation rows, the D1–D8 evidence index, and the persistent-URL
check it was generated beside. `cli/tests/test_lifecycle_report.py` holds the
committed report to itself: every video carries its run's policy and revision,
the operator check agrees with the run it selected, the comparison is
recomputable from the committed rows, every linked document, probe, test, ADR
and record node exists, and this page names every run whose retained model
view is incomplete. The project itself lives outside the checkout, so the
report is regenerated by hand and the test guards what was committed.

The narrative of each step, with its commands and failures, is
[`docs/HEADLESS-BIPED-REVIEW.md`](../../HEADLESS-BIPED-REVIEW.md); this page
links into it rather than repeating it.

## Training snapshots are not rollout views

The dashboard serves two different kinds of model for a run, and says which:

- **A rollout view** (`runs/<name>/rollout/*.stl`, "the rollout leg's exports
  at this run's revision") is the assembly at the first solved frame of the
  recorded trace, exported when the rollout ran. Every playback and walk run
  above has one, complete.
- **A training snapshot** ("assembled model retained before training",
  ADR-291) is the assembled model frozen when the trainer was dispatched, so
  a training record that never rolled out still shows the design it trained.
  It is never rebuilt from today's script. Two of them are incomplete:
  `probe3` retains **4 of 8** meshes and `shin55` **5 of 8**, because until
  ADR-302 the accepted model kept one tessellation per BREP digest and a
  mirrored pair of identical limbs shares a digest. The page labels the
  absent parts "mesh missing" rather than borrowing today's geometry, and
  the no-rebuild constraint means they stay that way. `copy100`'s frozen
  snapshot is partial for the same reason, but `copy100` has a rollout trace
  and the page prefers it.
- `probe2` predates ADR-291: its view is the retained training export parts
  at identity, not a solved pose, and the page says so (ADR-290).
- `probe1` has no view at all — no rollout trace, and no revision recorded
  to match the accepted model against — and the page gives the next CLI
  action instead of a model.

So when a reader compares `shin55`'s five-part snapshot with
`shin55-final`'s eight-part pose, they are looking at the same design at two
moments with two retention rules, not at two designs.

## Limits of this report

Everything here was observed on this machine over its private address; no
second device visited. `foot90` and `copy100` were actor-applied edits after
product-agent refusals and are labelled as such; the agent-authored revision
is `shin55`. No design walks; that is the measured result, not a gate.
Checkpoint resume does not exist. The evaluation rows for shin55 live in the
project copy `ot5-biped-shin55-seeds` and the compact summary here; the
videos, traces, checkpoints and screenshots stay project-local and must be
copied with the project.
